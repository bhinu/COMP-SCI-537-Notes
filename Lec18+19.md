## LECTURE 18: File System API

### High-level mental model

Three ways to name a file: inode number, path, file descriptor. Each came from a different design pressure.

- **Inode numbers** (L18-p3 to p5): unique, but unfriendly; offset semantics across processes are undefined.
- **Paths** (L18-p6 to p11): hierarchical, human-readable, but forcing a full path traversal on every read is expensive.
- **File descriptors** (L18-p23 to p25): traverse once on `open()`, then read/write via an in-memory struct that holds the inode pointer + offset.

Final API (L18-p24): `open`, `read`, `write`, `close`. Each process has an fd table of pointers into a system-wide open file table.

xv6 layout (L18-p25):
```c
struct file {
    struct inode *ip;
    uint off;
};
struct proc {
    struct file *ofile[NOFILE];   // per-process fd table
};
struct ftable { struct file file[NFILE]; }; // system-wide
```

### Path traversal cost (Tier 1 pattern in summary)

For `read /etc/bashrc`, opening requires 6 disk reads (L18-p20):
1. root inode
2. root directory data (find "etc")
3. etc inode
4. etc directory data (find "bashrc")
5. bashrc inode
6. bashrc data

General rule: depth-d path has `d+1` inode reads (root + each component) and `d` directory data reads. Total `2d + 1` reads in the cold case. Matches S23 Q24 (5 inodes for `/this/exam/is/hard`).

### File descriptor table semantics (Tier 2 pattern, S23 Q28 to Q31)

Three operations, three different sharing levels:

- **Two separate `open()` calls** of the same file: two distinct entries in the open file table. **Independent offsets.** (L18-p28)
- **`dup(fd)`**: new fd, **same** open file entry. **Shared offset.** (L18-p29)
- **`fork()`**: child gets a copy of the fd table. All entries point to the **same** open file objects in the system table. **Shared offsets across processes.** (L18-p32)

Practice from L18-p31, worked:
```
fd1 = open("file.txt"); // 12
fd2 = open("file.txt"); // 13   (separate entry)
read(fd1, buf, 16);     // fd1 offset = 16
fd3 = dup(fd2);         // 14, shares fd2's entry
read(fd2, buf, 16);     // fd2 AND fd3 offsets = 16 (shared)
lseek(fd1, 100, SEEK_SET);

Result:
- fd1 offset = 100
- fd2 offset = 16
- fd3 offset = 16   (shared with fd2)
```

### fsync, rename, atomic update

- `write()` returns once data is in OS memory; data may not be on disk. Only `fsync()` forces the page cache out and tells the disk to flush its write cache. (L18-p33)
- `rename(old, new)` replaces a path mapping. Does not move data. (L18-p34)
- Atomic update pattern (L18-p38):
  1. Write new contents to `file.tmp`
  2. `fsync(file.tmp)`
  3. `rename(file.tmp, file)`

If you skip the fsync, a crash between rename and disk flush can leave the new path pointing to a half-written file.

### Hard vs soft links (Tier 2 pattern)

| Property | Hard link | Soft link (symlink) |
|---|---|---|
| Stores | Same inode number | A path string |
| Survives target rename | Yes (still points to inode) | No (path is now stale) |
| Can link directories | No | Yes |
| Can cross filesystems | No | Yes |
| Refcount tracked | Yes (`link_count` in inode) | N/A |

A file's data is freed only when ALL hard links are unlinked AND no process has it open.

### Deletion semantics (L18-p42)

There is no "delete file" syscall. The inode is garbage collected when:
- All paths to it are unlinked, AND
- All open file descriptors to it are closed (or processes holding them exit).

Common idiom: open a file, unlink it, keep using the fd. Data lives until close. Useful for temp files that auto-clean.

### L18 flashcards

| Q | A |
|---|---|
| Disk reads to open `/a/b/c` cold? | 7 (root inode + root data + a inode + a data + b inode + b data + c inode); generally 2d+1 |
| After `fork()`, do parent and child share file offsets? | Yes. fd table copied, entries point to same open file objects |
| After two separate `open()` calls of the same file, do offsets share? | No. Each `open()` creates a new entry |
| After `dup(fd)`, do the two fds share the offset? | Yes. Both point to the same open file entry |
| What does `write()` guarantee about durability? | Nothing. Only `fsync()` makes it durable |
| Can a hard link cross filesystems? | No. Soft links can |
| Can you hard link a directory? | No (cycle risk). Soft links to dirs are fine |
| When is a file's inode actually freed? | When link count is 0 AND no open fds reference it |
| What is the atomic update idiom? | write tmp, fsync tmp, rename tmp over target |

## LECTURE 19: File Systems Implementation

### On-disk layout (L19-p42)

```
[Superblock] [Inode Bitmap] [Data Bitmap] [Inode Table] [Data Blocks ...]
```

- **Superblock**: FS metadata (block size, inode count). Read first on mount.
- **Inode bitmap**: 1 bit per inode (free/used).
- **Data bitmap**: 1 bit per data block.
- **Inode table**: array of inodes.
- **Data blocks**: file contents, directory data, indirect pointer blocks.

### Inode offset calculation (Tier 1 pattern)

Given 256-byte inodes and 4KB blocks: 16 inodes per block.

Inode `N` lives at:
- block index within inode region = `N / 16`
- byte offset within that block = `(N mod 16) * 256`

L19-p18 to p20 worked examples:
- Inode 0: block 0, offset 0
- Inode 4: block 0, offset 1024
- Inode 40: block 2, offset 2048

### Inode contents (L19-p30)

**Stored**: type (file or dir), uid, rwx, size, block count, atime, ctime, link_count, addrs[N].

**NOT stored**: filename, file extension, pointer to directory data. Summary's #1 gotcha applies directly.

### Allocation strategies (likely T/F territory)

| Strategy | Ext frag | Grow | Seq read | Random read | Metadata cost |
|---|---|---|---|---|---|
| Contiguous | Bad | Hard (predict size) | Excellent | Excellent | Tiny (start + size) |
| Few extents (2 to 6) | OK | Limited | Good | Good | Small array |
| Linked | None | Easy | Layout-dependent | O(n), terrible | 1 ptr per block |
| FAT | None | Easy | Decent if cached | Good if FAT cached | Whole FAT |
| Indexed | None | Easy | Good | Good | Index block per file |
| Multi-level indexed | None | Easy | Good | Good (small files) | Grows with file |

T/F traps:
- "Contiguous suffers more external fragmentation than extents." **TRUE** (quiz answer L19-p51).
- "Linked allocation supports O(1) random access." **FALSE** (must walk pointers from start).
- "FAT requires reading two disk locations per data read in the uncached case." **TRUE**.

### Multi-level indexing (Tier 1 pattern)

Inode holds direct + indirect + double indirect + triple indirect pointers. Indirect blocks live in regular data blocks and hold pointers (not data).

**Max file size formula**:
```
(D + N + N^2 + N^3) * B
  D = number of direct pointers
  N = pointers per indirect block = block_size / pointer_size
  B = block size
```

Worked from L19-p51:
- 4KB block, 4 direct, 1 indirect, 4-byte ptrs: D=4, N=1024, B=4KB. Max = `4·4KB + 1024·4KB = 16 + 4096 = 4112 KB`. Slide confirms.
- 1KB block, 4 direct, 1 indirect, 4-byte ptrs: D=4, N=256, B=1KB. Max = `4·1KB + 256·1KB = 260 KB`.

> **Slide typo flag**: L19-p51 writes 258 KB for the 1KB case, but the formula gives 260 KB. Your summary table also lists 260 KB. Trust the formula.

### Directories (L19-p36 to p37)

Stored as data blocks of entries. Format varies (lists, b-trees). Each entry: valid bit, name, inode number.

`unlink("foo")` clears the valid bit on foo's directory entry. Inode is freed only when no other paths AND no open fds reference it.

### FS operations: disk I/O traces (likely MC source)

These traces are prime question material.

- **open /foo/bar** (L19-p45): 5 reads. root inode, root data, foo inode, foo data, bar inode.
- **read /foo/bar** (already opened, L19-p46): 1 read (data) + 1 read (indirect if needed) + 1 write (atime on inode).
- **close /foo/bar** (L19-p47): 0 disk ops.
- **create /foo/bar** (L19-p48): 10 ops total. 5 reads to traverse + 5 writes (inode bitmap, new inode, foo dir data, foo inode, data bitmap if data block allocated).
- **write to /foo/bar** opened, allocating new block (L19-p49): 5 ops. Read inode, read data bitmap, write data bitmap, write data, write inode.

L19-p51 quiz: "create `/537/midterm-answers` + 1 data block, how many blocks updated?" Answer: **6 writes**.
1. inode bitmap (mark new inode used)
2. data bitmap (mark new data block used)
3. midterm-answers new inode
4. /537 directory data (add new entry)
5. /537 directory inode (size, mtime updated)
6. data block itself

This is the count of WRITES. Reads for traversal are excluded.

### L19-p51 quiz walkthrough (memorize, very testable)

- Open file in process P, P forks C, P unlinks the file, P exits, C exits. **When is the inode freed? When C exits.** The unlink removes the path but C still holds the fd. Refcount = paths + open fds.
- Create + 1 data block = 6 writes (above).
- 4KB block, 4 direct + 1 indirect, 4-byte ptr = **4112 KB**.
- 1KB block, 4 direct + 1 indirect, 4-byte ptr = **260 KB** (slide says 258, typo).
- "Contiguous has more external fragmentation than extents." **TRUE**.

## Predicted questions

### True / False (15)

1. After two separate `open()` calls on the same file, both fds share an offset. **F**
2. After `fork()`, parent and child share file offsets for fds inherited from the parent. **T**
3. After `dup()`, the two fds share an offset. **T**
4. `write()` guarantees data is on disk before returning. **F**
5. `fsync()` flushes both the OS page cache AND the disk's write cache. **T**
6. A hard link can be created across two different filesystems. **F**
7. A symbolic link can point to a directory. **T**
8. A file's inode is freed immediately when its only path is unlinked, even if a process still has it open. **F**
9. The filename is stored in the inode. **F**
10. Linked allocation supports O(1) random access. **F**
11. Contiguous allocation suffers worse external fragmentation than extent-based allocation. **T**
12. Reading an already-opened file requires zero disk reads if the inode and data are cached. **T**
13. Multi-level indexing requires the same number of disk accesses for any byte in the file. **F** (later bytes need more indirection)
14. The atomic update idiom needs an `fsync` before the rename to be safe across crashes. **T**
15. In FAT-based filesystems, caching the FAT in memory turns random access from O(n) into O(1). **T**

### Multiple choice (10)

**1.** Opening `/a/b/c/d` cold, how many inode reads?
(a) 4 (b) 5 (c) 8 (d) 9
**Answer: b** (root, a, b, c, d)

**2.** With 256-byte inodes and 4KB blocks, where is inode 17?
(a) block 0 offset 0 (b) block 1 offset 0 (c) block 1 offset 256 (d) block 2 offset 0
**Answer: c** (17/16 = block 1; 17 mod 16 = 1; 1·256 = 256)

**Answer: c** (12·4KB + 1024·4KB = 48 + 4096 = 4144)

**4.** 1KB blocks, 4-byte pointers, 4 direct + 1 indirect. Max file size?
(a) 256 KB (b) 258 KB (c) 260 KB (d) 1024 KB
**Answer: c** (4·1 + 256·1 = 260). Note: L19-p51 slide writes 258 (typo).

**5.** A process opens `f`, forks, parent unlinks `f` then exits. Child still has `f` open. When is the inode freed?
(a) immediately on unlink (b) when the parent exits (c) when the child exits or closes the fd (d) never, FS is corrupted
**Answer: c**

**6.** Which allocation strategy has the BEST sequential read throughput with cold cache?
(a) Linked (b) FAT (c) Contiguous (d) Multi-level indexed
**Answer: c**

**7.** Which has the WORST random read latency?
(a) Contiguous (b) Indexed (c) Linked (d) Multi-level indexed
**Answer: c**

**8.** How many disk WRITES to create a new file with 1 data block in a parent directory whose data block has space?
(a) 4 (b) 5 (c) 6 (d) 7
**Answer: c**

**9.** After `read(fd1, buf, 16)` followed by `int fd3 = dup(fd2)`, what is the offset of fd3 if fd2 was just opened from scratch?
(a) 0 (b) 16 (c) depends on fd1 (d) undefined
**Answer: a** (fd2 was a fresh open at offset 0; fd3 inherits fd2's entry)

**10.** Which of the following is NOT in an inode?
(a) file size (b) link count (c) filename (d) block pointers
**Answer: c**

## Formula sheet (slide-anchored)

```
Path traversal reads (cold) = 2d + 1
  where d = path depth (number of components after root)
  [L18-p20]

Inode location (B-byte inodes, K-byte blocks):
  inodes_per_block = K / B
  block index      = N / inodes_per_block
  byte offset      = (N mod inodes_per_block) * B
  [L19-p17 to p20]

Pointers per indirect block = block_size / pointer_size
  [L19-p35]

Max file size (multi-level indexed):
  (D + N + N^2 + N^3) * block_size
  D = direct pointers in inode
  N = pointers per indirect block
  [L19-p35, p51]

Quick checks:
  4KB block, 4-byte ptr, 12 direct + 1 indirect + 1 double indirect = ~4 GB
  4KB block, 4-byte ptr,  4 direct + 1 indirect                     = 4112 KB
  1KB block, 4-byte ptr,  4 direct + 1 indirect                     = 260 KB
                                                                       ^ slide typo says 258

Disk ops for FS operations:
  open /a/b/c       = 2d + 1 reads          [L19-p45]
  read (cached)     = 1R (data) + 1W (atime, optional)
  close             = 0 ops                  [L19-p47]
  create + 1 block  = 6 writes (traversal cached) [L19-p51]
  write + new block = 5 ops (1R inode + 1R bitmap + 1W bitmap + 1W data + 1W inode) [L19-p49]
```
